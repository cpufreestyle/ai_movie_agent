## fp16-vae 烟测验证：VAE 精度不是根因，cu130 才是

用户贴出 cu130 警告后，怀疑 Wan VAE 在 bf16 下崩；先以 `--fp32-vae` 重启 8200：KSampler 30/30 正常完成（2:46），但 fp32 VAE（2688MB）+ 模型 offload 把 32GB 内存撑到只剩 **737MB**，swap 抖动导致 VAE 解码数分钟不写盘——**fp32 让解码正确但环境不可行**（撑爆 RAM + cu128 优化算子被禁用走极慢 eager）。

改以 `--fp16-vae` 重启 8200（实例健康）：VAE 仅 1344MB（半），RAM 恢复到 ~3.4GB，采样 2:40 + fp16 解码快速，shot1 整轮 ~3 分钟完成（449.9KB webm）。**但抽中间帧验证内容仍是带色噪声纹理**（浅米黄带隐约竖纹，见 `outputs/shots_probe/shot1_fp16_t50.png`），与 bf16 时的棕色噪声本质相同——只是 VAE 精度让色相略变。

**结论闭环**：
1. VAE 精度（bf16/fp16/fp32）**不是**噪声根因——latent 本身在 cu128 下就是垃圾，三种 VAE 解码出来都只是"带色噪声"。
2. 真正根因是 **PyTorch cu128 < 13 → `comfy/quant_ops.py` 调 `ck.registry.disable("cuda")` → `comfy_kitchen` CUDA 后端被禁用 → Wan2.2 GGUF 的 fp8/UNet 算子在 Blackwell（sm_120）上跑错**。用户贴的 cu130 警告是**真凶**。
3. 唯一正解：把 ComfyUI venv 的 PyTorch 升到 **cu130**（`pip install --upgrade torch torchvision --index-url https://download.pytorch.org/whl/cu130`）。

## 路径 B 结论（更正上面"gating"判断）：Wan2.2-T2V-5B GGUF 根本不存在

用户提供 HF token 后实测核实（2026-09-03 晚）：
